## Findings

### Finding 1: Unrestricted server-side request forgery (full-read) via the article URL — `backend/app/modules/scraper/extractor.py:44`

- Severity: High
- Confidence: 0.85
- Category: ssrf
- Description: `POST /api/process` and `POST /api/bias` (`backend/app/routes/routes.py:62-75`)
  accept an arbitrary `url: str` from an unauthenticated caller and pass it unchanged to
  `run_scraper_pipeline` (`backend/app/modules/pipeline.py:48-50`). `Article_extractor` then
  fetches it server-side three ways: `trafilatura.fetch_url(self.url)` (line 52),
  newspaper3k `Article(self.url).download()` (lines 69-70) and `requests.get(self.url, ...)`
  (line 44). There is no scheme allow-list, no hostname/IP validation (loopback, RFC 1918,
  link-local `169.254.0.0/16`, IPv6 ULA/link-local), no DNS-rebinding protection, and redirects
  are followed by default, so a public URL can bounce the fetch to an internal one. The only
  http/https check lives in the browser (`frontend/app/[locale]/page.tsx:153-159`), which is
  not a trust boundary; the API is called directly. The response is read back to the attacker:
  `/api/process` returns the full LangGraph state, which includes `cleaned_text` (the extracted
  body of the fetched resource, `backend/app/modules/langgraph_nodes/store_and_send.py:38`), and
  the fetched text is also sent to Groq and summarised into the returned perspective and facts.
- Exploit Scenario: An attacker sends
  `curl -X POST https://<space>.hf.space/api/process -d '{"url":"http://127.0.0.1:<port>/..."}'`
  (or a URL on an attacker-controlled host that 302-redirects to an internal address, such as a
  cloud metadata endpoint or a service on the Space's private network). The backend fetches the
  internal resource and returns its extracted text in `cleaned_text`. Any self-hosted or Docker
  deployment (which the README encourages) exposes whatever is reachable from that host, such as
  admin panels, databases with HTTP interfaces and cloud instance-metadata credentials. What is
  actually reachable from the Hugging Face Spaces sandbox could not be verified statically.
- Recommendation: Validate the URL server-side before any fetch: parse it with
  `urllib.parse`, allow only `http`/`https`, resolve the hostname with `socket.getaddrinfo` and
  reject the request if any resolved address is loopback, private, link-local, reserved,
  multicast or unspecified (`ipaddress.ip_address(a).is_global` must be true). Perform the fetch
  once, yourself, with `requests` using `allow_redirects=False` and re-validating every
  `Location` hop (or pin the connection to the validated IP to defeat DNS rebinding). Then pass
  the downloaded HTML to `trafilatura.extract(html)` / `newspaper.Article(...).set_html(html)` /
  `readability.Document(html)` instead of letting each library fetch the URL itself. Also cap
  the response size (stream with a byte limit) and stop returning `cleaned_text` in the
  `/api/process` response if the frontend does not need it.

## Notes

### Note 1: Public, unauthenticated API with wildcard CORS and a shared RAG index — `backend/main.py:41`

- Category: design-tradeoff
- Observation: The FastAPI app registers `CORSMiddleware` with `allow_origins=["*"]` and
  `allow_credentials=True` (`backend/main.py:41-47`), and none of `/api/process`, `/api/bias`
  or `/api/chat` (`backend/app/routes/routes.py:62-85`) has an authentication dependency. Any
  website or script can therefore drive the API, and `/api/chat` answers from a single shared
  Pinecone namespace (`"default"`, `backend/app/modules/chat/get_rag_data.py:41-43`), so the
  counter-perspective reasoning and fact-check explanations generated for one visitor's article
  are retrievable by every other caller. Because the backend uses no cookies or other ambient
  credentials, the wildcard CORS policy does not expose any per-user data, and no
  user-specific data is stored.
- Rationale: The project deliberately runs as a free, sign-in-free public tool: the UI states
  "No sign in required. It's completely free." (`frontend/messages/en.json:28`), and the
  published plugin manifest declares `"auth": {"type": "none"}` and
  `"is_user_authenticated": false` (`frontend/public/.well-known/ai-plugin.json`). Adding
  authentication would contradict that stated design. If the shared index should not mix
  visitors' results, scope retrieval by `article_id` (already stored in chunk metadata) and send
  it from the frontend with each chat message. The wildcard CORS with `allow_credentials=True`
  should be reconsidered if cookies or auth are ever added.

## Limitations

**Standing limitations**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at runtime,
  so timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed
  here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated statistical
  probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into
  some models can cause a real vulnerability to be softened, generalized, or left out rather
  than reported in exploit-level detail, and training-data bias can make some vulnerability
  classes easier for a model to recognize than others. Treat this report as a floor on what a
  full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very
  recently disclosed CVE or library advisory may not be recognized as such.

**Review-specific limitations**

- The network environment of the Hugging Face Space (which internal addresses, metadata
  endpoints or sibling services are reachable from the container) is external state that was
  not available, so the real-world impact of Finding 1 on the hosted deployment could not be
  confirmed; the severity assumes a typical self-hosted or cloud deployment.
- The source of third-party fetchers (trafilatura, newspaper3k, readability-lxml) was not
  reviewed; redirect-following and size-limit behaviour is stated from their documented
  defaults, not from the installed versions.
- Repository-level GitHub settings (default `GITHUB_TOKEN` permissions, branch protection on
  `main`, who can push) were unavailable; the workflow review covers only the YAML files.
- No exploit-level detail was held back because of a content restriction.
